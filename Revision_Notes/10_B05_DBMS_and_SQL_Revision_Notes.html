📖 Chapter 1: Concepts & Architecture — ANSI/SPARC 3-Schema Architecture, Data Independence & Database Users/DBA

3 Questions in Booklet
📌 1.1 ANSI/SPARC 3-Schema Architecture, Data Independence & Database Users/DBA
Key Formulas & Rules
  • 🔹 3 Schemas: External / View Level (User Views) <-> Conceptual / Logical Level (Tables/Relations/Constraints) <-> Internal / Physical Level (B+ Trees/Hashing/Blocks)
Simple Exam Points
  • DBMS advantages over traditional Flat-File Systems include elimination of data redundancy & inconsistency, atomic transaction recovery, concurrent access control, and declarative integrity enforcement.
  • The 3-Schema Architecture provides two levels of Data Independence: (1) Physical Data Independence (ability to modify the Internal/Physical schema—e.g., changing file organization from heap to B+ tree or moving data files—without altering the Conceptual schema or application programs)
  • (2) Logical Data Independence (ability to modify the Conceptual schema—e.g., adding/splitting tables or attributes—without altering External user views).
  • Logical Data Independence is harder to achieve because application programs are tightly coupled to the logical structure.
✅ Direct Exam Example: Database Metadata & System Catalog: The Data Dictionary (System Catalog) stores metadata (definitions of tables, columns, data types, views, indexes, and user privileges) and is itself stored and queried as relational tables by the Query Optimizer.
💡 Exam Shortcut / Trap: Hinglish Tip: Physical Data Independence (Internal <-> Conceptual) achieve karna aasan hai, jabki Logical Data Independence (Conceptual <-> External View) achieve karna zyada kathin (harder) hota hai!

📖 Chapter 2: Relational Model & Keys — Relational Model, Keys (Super, Candidate, Primary, Alternate, Foreign) & Relational Algebra

19 Questions in Booklet
📌 2.1 Relational Model, Keys (Super, Candidate, Primary, Alternate, Foreign) & Relational Algebra
Key Formulas & Rules
  • 🔹 Number of Superkeys for n attributes: (1) Single 1-attr CK -> 2^(n−1); (2) Two disjoint 1-attr CKs A, B -> 2^(n−1) + 2^(n−1) − 2^(n−2);
  • 🔹 Alternate Keys = Candidate Keys − Primary Key
Simple Exam Points
  • Relational Integrity Constraints: (1) Entity Integrity Rule: No attribute participating in the Primary Key can ever be NULL!
  • (2) Referential Integrity Rule: A Foreign Key value must either match an existing Primary Key value in the referenced parent tuple OR be wholly NULL (Note: Primary Key allows 0 NULLs
  • UNIQUE key in SQL allows NULLs
  • Foreign Key allows duplicates and NULLs!).
  • Core Relational Algebra Operators (6 Fundamental Operators): Selection (σ — horizontal row filter, commutative), Projection (π — vertical column filter, eliminates duplicate rows automatically!), Cartesian Product (×), Union (∪), Set Difference (−), and Rename (ρ).
  • Derived Operators: Natural Join (⋈), Division (÷ — used for 'for all / every' universal queries!).
✅ Direct Exam Example: Worked Join Cardinality & Superkey Math: Relation R(A,B,C,D,E) has n=5 attributes and two Candidate Keys {A} and {B,C}. Superkeys containing A = 2^(5−1) = 16; Superkeys containing BC = 2^(5−2) = 8; Overlap containing ABC = 2^(5−3) = 4. Total Superkeys = 16 + 8 − 4 = 20! Also for Natural Join of R (m tuples) and S (n tuples): If common attribute is PK of R and FK of S, join size is exactly n tuples.
💡 Exam Shortcut / Trap: Exam Trap: Relational Algebra ka Projection operator (π) automatically DUPLICATE rows hata deta hai (kyunki relation ek mathematical Set hai), jabki SQL ka `SELECT` bina `DISTINCT` keyword ke duplicates retain rakhta hai (Multiset/Bag)!

(B) 16 Superkeys
(C) 4 Superkeys
(D) 1 Superkey
Answer (A): Any subset of the remaining `n − k = 3` non-key attributes `{B, C, D}` combined with Candidate Key `A` forms a Superkey => `2³ = 8` superkeys.

(A) Every Superkey is a Candidate Key
(B) A Candidate Key is a MINIMAL Superkey ✅
(C) A Table can have only one Candidate Key

Answer (B): A Candidate Key is a MINIMAL Superkey (no proper subset of a Candidate Key is itself a Superkey) — Every Candidate Key is a Superkey, but not every Superkey is a Candidate Key. One chosen Candidate Key becomes the Primary Key (the remaining Candidate Keys are Alternate Keys).
Q2.4: Which Integrity Constraint states that 'No attribute participating in the Primary Key of a base relation is allowed to accept NULL values'?
(A) Referential Integrity Constraint (Foreign Key)
(B) Domain Integrity Constraint
(C) Entity Integrity Constraint ✅
(D) Tuple Uniqueness Constraint
Answer (C): Entity Integrity = Primary Key cannot be NULL; Referential Integrity = Foreign Key must either match an existing Primary Key value or be NULL.
Q2.5: Which six operators form the 'Fundamental (Minimal Complete) Set' of Relational Algebra operators?

(B) SUM, AVG, COUNT, MIN, MAX
(C) INSERT, UPDATE, DELETE
(D) Select (σ), Project (π), Union (∪), Set Difference (−), Cartesian Product (×), and Rename (ρ) ✅
Answer (D): Join (`⋈ = σ(R × S)`), Intersection (`R ∩ S = R − (R − S)`), and Division (`÷`) are Derived operators.

📖 Chapter 3: SQL & Queries — SQL Sublanguages (DDL, DML, DCL, TCL), Execution Order, Aggregates & Joins

13 Questions in Booklet
📌 3.1 SQL Sublanguages (DDL, DML, DCL, TCL), Execution Order, Aggregates & Joins
Key Formulas & Rules
  • 🔹 SQL Sublanguages: DDL (CREATE, ALTER, DROP, TRUNCATE, RENAME)
  • 🔹 DML (SELECT, INSERT, UPDATE, DELETE)
  • 🔹 DCL (GRANT, REVOKE)
  • 🔹 TCL (COMMIT, ROLLBACK, SAVEPOINT)
Simple Exam Points
  • Logical SQL Query Execution Order: `FROM / JOIN` -> `WHERE` (filters individual rows before grouping
  • cannot contain aggregate functions!) -> `GROUP BY` -> `HAVING` (filters grouped aggregates) -> `SELECT` -> `DISTINCT` -> `ORDER BY` -> `LIMIT/FETCH`.
  • All 5 SQL Aggregate Functions (`COUNT`, `SUM`, `AVG`, `MIN`, `MAX`) strictly IGNORE `NULL` values, EXCEPT `COUNT(*)` which counts all rows including rows with NULLs!
  • Key Comparison: `DELETE` (DML, row-by-row logged, supports `WHERE` clause, can be rolled back, triggers fire) vs `TRUNCATE` (DDL, deallocates data pages in bulk, no `WHERE` clause, resets identity, faster) vs `DROP` (DDL, removes entire table data + schema structure from catalog).
✅ Direct Exam Example: Worked SQL Output: Table Emp has 5 rows with Commission values: `[100, 200, NULL, 300, NULL]`. Then `SELECT COUNT(*), COUNT(Comm), AVG(Comm) FROM Emp;` returns: `COUNT(*) = 5`, `COUNT(Comm) = 3`, and `AVG(Comm) = (100+200+300)/3 = 200` (NOT 600/5 = 120!).
💡 Exam Shortcut / Trap: Hinglish Tip: `WHERE` clause `GROUP BY` se pehle chalta hai aur rows ko filter karta hai (isliye `WHERE` me `SUM/COUNT` likhna syntax error hai); `HAVING` clause `GROUP BY` ke baad groups ko filter karta hai! Aur `NULL = NULL` ya `NULL <> NULL` hamesha UNKNOWN (falsy) return karta hai — hamesha `IS NULL` ya `IS NOT NULL` use karein!

Q3.1: Classify the SQL commands `CREATE, ALTER, DROP, TRUNCATE` vs `SELECT, INSERT, UPDATE, DELETE`:
(A) TRUNCATE is DML and DELETE is DDL
(B) INSERT is DDL and CREATE is DML

CREATE, ALTER, DROP, TRUNCATE = DDL (Data Definition Language); SELECT, INSERT, UPDATE, DELETE = DML (Data Manipulation Language) — DDL defines/modifies schema structure (auto-commits); DML queries/modifies row data; DCL = `GRANT, REVOKE`; TCL = `COMMIT, ROLLBACK, SAVEPOINT`.

(A) TRUNCATE supports a WHERE clause to delete selected rows
(B) DROP keeps the table columns and deletes only rows
(C) DELETE removes the table schema from the database
(D) DELETE (DML) removes rows one-by-one using a WHERE clause ✅
Answer (D): DELETE (DML) removes rows one-by-one using a WHERE clause; TRUNCATE (DDL) deallocates all data pages at once keeping the table schema; DROP (DDL) deletes the entire table data AND schema structure. DELETE (DML) removes rows one-by-one using a WHERE clause (fires triggers, can be rolled back); TRUNCATE (DDL) deallocates all data pages at once keeping the table schema; DROP (DDL) deletes the entire table data AND schema structure — `TRUNCATE TABLE` is a fast DDL command that removes all rows without a `WHERE` clause and resets auto-increment counters; `DROP TABLE` removes the table itself.
Q3.3: In an SQL query containing `WHERE`, `GROUP BY`, `HAVING`, and `ORDER BY`, what is their correct syntactic and logical execution order?
(A) Syntactic order: SELECT -> FROM -> WHERE -> GROUP BY -> HAVING -> ORDER BY ✅
(B) GROUP BY comes before WHERE
(C) HAVING comes before GROUP BY
(D) ORDER BY executes before WHERE
Answer (A): Syntactic order: SELECT -> FROM -> WHERE -> GROUP BY -> HAVING -> ORDER BY (Logical execution: FROM -> WHERE -> GROUP BY -> HAVING -> SELECT -> ORDER BY) — `WHERE` filters individual rows BEFORE grouping (cannot contain aggregate functions); `HAVING` filters aggregated groups AFTER `GROUP BY`.
Q3.4: In SQL, how do the aggregate functions `COUNT(*)` vs `COUNT(column_name)` handle `NULL` values?
(A) Both COUNT(*) and COUNT(col) ignore NULL rows
(B) `COUNT(*)` counts ALL rows including rows with NULLs ✅
(C) COUNT(col) counts only NULL values
(D) AVG(col) treats NULL as 0
Answer (B): `COUNT(*)` counts ALL rows including rows with NULLs; `COUNT(column_name)` ignores NULL values in that column. `COUNT(*)` counts ALL rows including rows with NULLs; `COUNT(column_name)` (as well as SUM, AVG, MIN, MAX) ignores NULL values in that column — If a table has 5 rows with column `Bonus = {100, 200, NULL, 300, NULL}`, then `COUNT(*) = 5`, `COUNT(Bonus) = 3`, and `AVG(Bonus) = 600 / 3 = 200` (not 600/5)!
Q3.5: In SQL 3-Valued Logic (`TRUE, FALSE, UNKNOWN`), which operator must be used in a `WHERE` clause to test whether a column value is `NULL`?
(A) `= NULL`
(B) `== NULL`
(C) `IS NULL` ✅
(D) `!= NULL`
Answer (C): `IS NULL` (or `IS NOT NULL`) — In SQL, any arithmetic or comparison with `NULL` (`x = NULL` or `NULL = NULL`) evaluates to `UNKNOWN`, so `WHERE col IS NULL` must be used.

📖 Chapter 4: ER Model Basics — Entity-Relationship (ER) Model — Cardinalities, Participation & Minimum Relational Tables

4 Questions in Booklet
📌 4.1 Entity-Relationship (ER) Model — Cardinalities, Participation & Minimum Relational Tables
Key Formulas & Rules
  • 🔹 Minimum Tables for Binary Relationship between E1 and E2: (1) 1:1 -> 1 or 2 tables
  • 🔹 (2) 1:N -> 2 tables (merge into N-side!)
  • 🔹 (3) M:N -> 3 tables (separate junction table mandatory!)
Simple Exam Points
  • Peter Chen's ER Diagram Notation: Rectangle = Strong Entity Set
  • Double Rectangle = Weak Entity Set (lacks sufficient attributes to form a Primary Key
  • depends on an Identifying Owner Entity via a Double Diamond Identifying Relationship with TOTAL Participation = Double Line, and has a Partial Key / Discriminator underlined with a dashed line)
  • Ellipse = Attribute
  • Double Ellipse = Multivalued Attribute (becomes a SEPARATE table in relational mapping!)
  • Dashed Ellipse = Derived Attribute (e.g., Age from DOB)
  • Composite Attribute = Flattened into constituent atomic columns.
✅ Direct Exam Example: Worked Table Reduction: An ER diagram has Strong Entities A and B connected by a 1:N relationship R (1 on A, N on B), plus B has a multivalued attribute Phone. Minimum relational tables = 1 (for A) + 1 (for B merged with R, placing A's PK as FK in B) + 1 (separate table for B's multivalued Phone) = 3 tables.
💡 Exam Shortcut / Trap: Exam Trap: Weak Entity Set ki Participation identifying relationship me hamesha TOTAL (Double Line) hoti hai! Aur M:N relationship ya Multivalued Attribute ko relational schema me badalne par hamesha ek NAYA separate table banta hai!

📖 Chapter 5: Normalization — Functional Dependencies, Attribute Closure (X+) & Normal Forms (1NF, 2NF, 3NF, BCNF, 4NF)

8 Questions in Booklet
📌 5.1 Functional Dependencies, Attribute Closure (X+) & Normal Forms (1NF, 2NF, 3NF, BCNF, 4NF)
Key Formulas & Rules
  • 🔹 1NF: Atomic values
  • 🔹 2NF: No Partial Dependency (Non-Prime -> Proper subset of CK)
  • 🔹 3NF: For X -> A, X is Superkey OR A is Prime
  • 🔹 BCNF: For X -> A, X MUST be Superkey!
Simple Exam Points
  • Armstrong's Axioms: Reflexivity (if Y ⊆ X then X -> Y), Augmentation (if X -> Y then XZ -> YZ), Transitivity (if X -> Y and Y -> Z then X -> Z).
  • Normalization Hierarchy: Every BCNF relation is in 3NF, every 3NF is in 2NF, and every 2NF is in 1NF.
  • Important Theorem: Any relation with only 2 attributes is ALWAYS in BCNF!
  • If every Candidate Key of a relation is a single simple attribute (1 column), the relation is guaranteed to be in 2NF (since no proper subset of a 1-attribute key exists).
  • Lossless-Join Decomposition is ALWAYS achievable for BCNF
  • Dependency Preservation is ALWAYS achievable for 3NF, but NOT always achievable for BCNF!
  • 4NF eliminates Multi-Valued Dependencies (X ->> Y)
  • 5NF (PJNF) eliminates Join Dependencies.
✅ Direct Exam Example: Worked Normal Form Check: Given R(A, B, C, D) with FDs `{AB -> CD, C -> A}`. Find Candidate Keys: B and D never appear on RHS, so every CK must contain BD. Check (BD)+ = BD (not all). Check (BCD)+ = BCDA (CK1 = BCD); Check (ABD)+ = ABCD (CK2 = ABD). Prime attributes = {A, B, C, D}! Now check `C -> A`: LHS `C` is NOT a superkey (violates BCNF!), but RHS `A` is a Prime Attribute (satisfies 3NF!). Highest Normal Form = 3NF.
💡 Exam Shortcut / Trap: Hinglish Tip: 3NF vs BCNF ka ek-line farq: BCNF me har FD `X -> Y` ka LHS (`X`) 100% Superkey hona hi chahiye; 3NF me ek chhoot (relaxation) milti hai ki agar RHS (`Y`) Prime Attribute (Candidate Key ka hissa) ho, to LHS Superkey na hone par bhi 3NF valid rehta hai!

Q5.1: Which set of three sound and complete inference rules (Reflexivity, Augmentation, Transitivity) is used to derive all implied Functional Dependencies `F⁺`?

(B) Codd's 12 Rules
(C) Coffman's Rules

(B) It has no Transitive Dependency
(C) It has no Partial Dependency

Q5.3: What is the strict condition for a relation to be in Boyce-Codd Normal Form (BCNF / 3.5NF)?
(A) X can be a non-prime attribute if Y is prime
(B) For EVERY non-trivial Functional Dependency `X -> Y`, the determinant `X` MUST be a Superkey ✅
(C) It only removes multivalued dependencies
(D) It allows partial dependencies
Answer (B): BCNF is strictly stronger than 3NF: even if `A` is a Prime attribute, `X -> A` violates BCNF unless `X` is a Superkey.
Q5.4: Which Normal Form is violated by non-trivial Multi-Valued Dependencies (`X ->> Y`), and which Normal Form is based on Join Dependencies (`JD`)?
(A) 2NF eliminates MVDs and 3NF eliminates Join Dependencies
(B) BCNF eliminates MVDs
(C) 4NF eliminates Multi-Valued Dependencies (`X ->> Y`) ✅
(D) 1NF is higher than 5NF
Answer (C): 4NF eliminates Multi-Valued Dependencies (`X ->> Y`); 5NF eliminates Join Dependencies. 4NF eliminates Multi-Valued Dependencies (`X ->> Y`); 5NF (Project-Join Normal Form / PJNF) eliminates Join Dependencies — Memorize the hierarchy: `5NF (Join Dep) => 4NF (MVD) => BCNF (Determinant = Superkey) => 3NF (No Transitive) => 2NF (No Partial) => 1NF (Atomic)`.
Q5.5: Compare 3NF Decomposition vs BCNF Decomposition regarding Lossless-Join and Dependency Preservation:
(A) BCNF is always Dependency-Preserving and 3NF is not
(B) Neither 3NF nor BCNF can be Lossless-Join
(C) Both are always Dependency-Preserving
(D) 3NF Decomposition can ALWAYS be made both Lossless-Join AND Dependency-Preserving ✅
Answer (D): 3NF Decomposition can ALWAYS be made both Lossless-Join AND Dependency-Preserving; BCNF Decomposition is always Lossless-Join, but is NOT always Dependency-Preserving. Classic exam point: Every relation has a Lossless + Dependency-Preserving decomposition into 3NF, whereas BCNF guarantees Lossless Join but may sacrifice Dependency Preservation (e.g., `AB -> C, C -> B`).

📖 Chapter 6: Transactions & ACID — Transactions, ACID Properties, Concurrency Anomalies, Serializability & 2PL / Timestamp Protocols

7 Questions in Booklet
📌 6.1 Transactions, ACID Properties, Concurrency Anomalies, Serializability & 2PL / Timestamp Protocols
Key Formulas & Rules
  • 🔹 Number of Serial Schedules for n transactions = n!
  • 🔹 Conflict Equivalent -> Acyclic Precedence (Serialization) Graph
  • 🔹 ACID: Atomicity (Log/Recovery), Consistency, Isolation (Concurrency), Durability
Simple Exam Points
  • Concurrency Anomalies: Dirty Read (W-R conflict: reading uncommitted data that later rolls back), Unrepeatable Read (R-W conflict), Lost Update (W-W conflict), Phantom Read.
  • Conflict Serializability checks conflicting pairs (same data item Q, different transactions, at least one is Write: R-W, W-R, W-W) to build a Precedence Graph
  • if the graph has NO cycles (DAG), the schedule is Conflict Serializable (and thus View Serializable).
  • Strict Two-Phase Locking (Strict 2PL — holds all exclusive Write locks until Commit/Abort) guarantees both Conflict Serializability AND Cascadeless Recoverability, though 2PL can suffer from Deadlocks.
  • Wound-Wait (preemptive) and Wait-Die (non-preemptive) use timestamps to prevent deadlocks.
✅ Direct Exam Example: Undo / Redo Write-Ahead Logging (WAL) Recovery: In Immediate Database Modification, transactions with `<T_i start>` AND `<T_i commit>` in the log before crash undergo REDO(T_i); transactions with `<T_i start>` but NO `<T_i commit>` undergo UNDO(T_i).
💡 Exam Shortcut / Trap: Exam Trap: Har Conflict Serializable schedule View Serializable hota hai, par har View Serializable schedule Conflict Serializable NAHI hota (agar usme 'Blind Writes' hon)! Aur Strict 2PL Cascading Rollbacks ko 100% rokta hai.

(A) Addition, Calculation, Indexing, and Deletion
(B) Active, Connected, Indexed, and Distributed
(C) Access, Control, Identity, and Data
(D) Atomicity, Consistency, Isolation, and Durability ✅

(B) 1. Syntax Error, 2. Divide by Zero, 3. Overflow
(C) 1. 1NF, 2. 2NF, 3. 3NF
(D) 1. Deadlock, 2. Starvation, 3. Aging
Answer (A): 1. Dirty Read (WR Conflict — reading uncommitted data that later rolls back), 2. Unrepeatable Read (RW Conflict), and 3. Lost Update (WW Conflict) / Phantom Read — SQL Isolation Levels from weakest to strongest: `READ UNCOMMITTED` (allows Dirty Reads) -> `READ COMMITTED` -> `REPEATABLE READ` -> `SERIALIZABLE` (highest, prevents all anomalies).
Q6.3: How do we test whether a concurrent transaction schedule `S` is 'Conflict Serializable'?
(A) If the graph has a cycle, it is Conflict Serializable
(B) Construct the Precedence (Serialization) Graph with edges for conflicting operations ✅
(C) By counting the number of COMMIT statements
(D) Only if all transactions run on different tables
Answer (B): Construct the Precedence (Serialization) Graph with edges for conflicting operations; `S` is Conflict Serializable if and only if its Precedence Graph has NO CYCLES (is a DAG). Construct the Precedence (Serialization) Graph with edges for conflicting operations (`R-W, W-R, W-W` on same data item); `S` is Conflict Serializable if and only if its Precedence Graph has NO CYCLES (is a DAG) — If the Precedence Graph is acyclic (DAG), any **Topological Sort** of the DAG yields an equivalent Serial Schedule!
Q6.4: In Two-Phase Locking (2PL), what are the two phases, and which variant of 2PL holds all Exclusive (Write) locks until the transaction commits/aborts to prevent 'Cascading Rollbacks'?
(A) Basic 2PL prevents deadlocks
(B) Strict 2PL releases write locks before commit
(C) Growing Phase and Shrinking Phase ✅
(D) Rigorous 2PL releases all locks at the start
Answer (C): Growing Phase and Shrinking Phase; 'Strict 2PL' holds all Exclusive (X) locks until Commit/Abort. Growing Phase (acquire locks only) and Shrinking Phase (release locks only); 'Strict 2PL' holds all Exclusive (X) locks until Commit/Abort — Basic 2PL guarantees Conflict Serializability (ordered by lock points) but can suffer from Deadlocks and Cascading Rollbacks; **Strict 2PL** holds all Write (`X`) locks until Commit, guaranteeing Strict & Cascadeless schedules (Rigorous 2PL holds both `S` and `X` locks until Commit).
Q6.5: In Wait-Die and Wound-Wait timestamp-based deadlock prevention schemes (where an older transaction has a smaller timestamp `TS(T_old) < TS(T_young)`), which scheme is Non-Preemptive and which is Preemptive?
(A) Wait-Die is Preemptive and Wound-Wait is Non-Preemptive
(B) In both schemes, the older transaction is killed
(C) Both allow deadlocks to occur
(D) Wait-Die is Non-Preemptive; Wound-Wait is Preemptive ✅
Answer (D): Wait-Die is Non-Preemptive (Older waits for Younger; Younger dies/rolls back if requesting lock held by Older); Wound-Wait is Preemptive (Older wounds/preempts Younger; Younger waits for Older) — Easy Trick: Look at the FIRST word for what the OLDER transaction does when colliding with a younger one: **Wait**-Die -> Older *Waits*; **Wound**-Wait -> Older *Wounds (Preempts)*!

📖 Chapter 7: Indexing & Storage — File Organization, Primary/Clustering/Secondary Indexes & B-Tree vs B+ Tree Order Math

4 Questions in Booklet
📌 7.1 File Organization, Primary/Clustering/Secondary Indexes & B-Tree vs B+ Tree Order Math
Key Formulas & Rules
  • 🔹 B+ Tree Internal Node (Order p): p Block Pointers + (p − 1) Search Keys, satisfying ⌈p/2⌉ <= Pointers <= p
  • 🔹 Search/Insert/Delete = O(log_p N)
Simple Exam Points
  • Index Classification: (1) Primary Index = Ordered file on Ordering Key (Primary Key) -> Sparse Index (1 index entry per disk block)
  • (2) Clustering Index = Ordered file on Ordering Non-Key attribute (with duplicate values) -> Sparse Index
  • (3) Secondary Index = Unordered field (Candidate key or Non-key) -> MUST be a Dense Index (1 index entry per record)!
  • B-Tree vs B+ Tree: In a B-Tree, data record pointers are stored in BOTH internal and leaf nodes
  • in a B+ Tree (standard DBMS index), data pointers reside ONLY in Leaf Nodes (which are linked together in a doubly-linked sequential list for fast range queries `WHERE salary BETWEEN 50000 AND 90000`), while internal nodes hold only routing keys (giving higher fan-out and shallower tree height).
✅ Direct Exam Example: Worked B+ Tree Order Calculation: Disk block size = 1024 Bytes, Search key size K = 12 Bytes, Block pointer P_b = 8 Bytes. For a B+ Tree internal node of order p: p × 8 + (p − 1) × 12 <= 1024 => 20p − 12 <= 1024 => 20p <= 1036 => Max Order p = 51 pointers (50 keys per node).
💡 Exam Shortcut / Trap: Hinglish Tip: Database (MySQL InnoDB, Oracle, PostgreSQL) me hamesha B+ Tree use hota hai kyunki B+ Tree ke saare Leaf Nodes ek Linked List se jude hote hain jisse Range Queries (`BETWEEN`, `>`, `<`) super-fast chalti hain! Aur Secondary Index hamesha DENSE Index hota hai.

📝 Chapter 7 — Practice Questions & Simple Explanations

Q7.1: Why do all relational database engines (MySQL InnoDB, PostgreSQL, Oracle, SQL Server) use 'B+ Trees' rather than standard 'B-Trees' for disk table indexing?
(A) A B-Tree has linked leaf nodes and a B+ Tree does not
(B) A B+ Tree is a binary tree of maximum degree 2
(C) In a B+ Tree, internal nodes store ONLY routing keys, and ALL data pointers reside in the LEAF nodes which are linked together in a sequential Doubly-Linked List for fast range queries ✅
(D) A B+ Tree stores no keys in leaf nodes
Answer (C): In a B+ Tree, internal nodes store ONLY routing keys (no data records, maximizing fan-out and keeping tree height `h = 2–3`), and ALL data pointers reside in the LEAF nodes which are linked together in a sequential Doubly-Linked List for fast range queries (`WHERE salary BETWEEN 50000 AND 80000`) — B+ Tree = high internal node fan-out (shallow height -> fewer disk I/Os) + linked leaf nodes (O(1) sequential range scan after initial `O(log_B N)` lookup).
Q7.2: What is the difference between a 'Primary (Clustering) Index' and a 'Secondary (Non-Clustering) Index'?
(A) A table can have 10 Clustered Indexes
(B) A Secondary Index can be a Sparse Index
(C) A Primary Index requires unsorted data
(D) A table can have AT MOST ONE Primary/Clustered Index, whereas a table can have MANY Secondary (Non-Clustered) Indexes ✅
Answer (D): A table can have AT MOST ONE Primary/Clustered Index (because it dictates the actual physical sorted order of rows on disk), whereas a table can have MANY Secondary (Non-Clustered) Indexes (which are always Dense Indexes) — Because data rows can only be physically sorted in one order on disk, a table has at most 1 Clustered Index (Sparse index: 1 entry per disk block), while Secondary Indexes are on unsorted columns and MUST be Dense (1 entry per record).
Q7.3: In Write-Ahead Logging (WAL) database crash recovery, what must be flushed to stable disk BEFORE a modified data page is written to disk or a transaction is declared committed?
(A) The Undo/Redo Log Record must be written to stable disk BEFORE the corresponding data page is flushed to disk ✅
(B) Data pages are written first and log records are written a week later
(C) Logs are stored only in volatile CPU registers
(D) WAL deletes all log files on commit
Answer (A): In WAL / ARIES recovery: **UNDO** reverses uncommitted (loser) transactions for Atomicity; **REDO** replays committed (winner) transactions for Durability.
Q7.4: In a B-Tree of order `m` (maximum `m` children per node), what is the maximum number of keys per node and the minimum number of keys in any non-root internal node?
(A) Maximum keys = m; Minimum keys = 1
(B) Maximum keys = m − 1; Minimum keys in non-root node = ⌈m / 2⌉ − 1 ✅
(C) Maximum keys = 2m; Minimum keys = m
(D) Minimum keys = 0
Answer (B): Maximum keys = m − 1; Minimum keys in non-root node = ⌈m / 2⌉ − 1 (minimum children = ⌈m / 2⌉) — For a B-Tree of order `m = 5`: each node holds at most `5 − 1 = 4` keys (5 children) and at least `⌈5/2⌉ − 1 = 2` keys (3 children).
