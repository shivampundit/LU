📖 Chapter 1: SDLC Models — SDLC Process Models — Waterfall, V-Model, Prototyping, Incremental, Spiral (Boehm) & Agile Scrum

📌 1.1 SDLC Process Models — Waterfall, V-Model, Prototyping, Incremental, Spiral (Boehm) & Agile Scrum
Key Formulas & Rules
  • 🔹 Boehm's Spiral Model = 4 Quadrants per Loop (1. Objectives -> 2. Risk Analysis & Prototyping -> 3. Engineering & Testing -> 4. Customer Evaluation & Next Planning)
Simple Exam Points
  • SDLC Model Selection Criteria: (1) Classical Waterfall (Royce, 1970): Rigid sequential phases
  • suitable ONLY when requirements are 100% frozen, well-understood, and stable upfront
  • customer sees working software only at the very end
  • (2) Prototyping Model: Best when customer requirements are vague/unclear upfront
  • (3) RAD (Rapid Application Development): Component-based high-speed delivery in 60–90 days using reusable CASE tools
  • (4) Spiral Model (Barry Boehm, 1986): Meta-model driven by explicit RISK ANALYSIS at every loop — ideal for large, complex, high-risk systems
  • (5) Agile / Scrum: Iterative 2–4 week Sprints, Product Backlog, Daily Standup (15 min), welcomes changing requirements.
✅ Direct Exam Example: V-Model (Verification & Validation Mapping): Requirements Specification <-> Acceptance Testing; System/High-Level Design <-> System & Integration Testing; Detailed Module Design <-> Unit Testing.
💡 Exam Shortcut / Trap: Exam Trap: Agar question me 'Risk Analysis / Risk Handling' ya 'Meta-Model' shabd aaye, to 100% answer 'Spiral Model (Barry Boehm)' hoga! Aur agar 'Unclear/Ambiguous User Requirements' aaye, to 'Prototyping Model' hoga!

📖 Chapter 2: Requirements & SRS — Requirement Engineering, IEEE 830 SRS Characteristics & Verification vs Validation

📌 2.1 Requirement Engineering, IEEE 830 SRS Characteristics & Verification vs Validation
Key Formulas & Rules
  • 🔹 Verification ('Are we building the product RIGHT?') = Static Reviews/Inspections against SRS
  • 🔹 Validation ('Are we building the RIGHT product?') = Dynamic Execution against User Needs
Simple Exam Points
  • Requirement Engineering Phases: Elicitation (gathering) -> Analysis & Negotiation -> Specification (producing the SRS document — a legally binding black-box contract between customer and developer) -> Validation -> Management.
  • Per IEEE 830 standard, a good SRS must be Correct, Unambiguous (every requirement has ONLY ONE interpretation), Complete, Consistent, Ranked for importance/stability, Verifiable (testable), Modifiable, and Traceable (Forward and Backward Traceability Matrix).
✅ Direct Exam Example: Functional vs Non-Functional Requirements: Functional specifies WHAT the system transforms (inputs -> outputs), whereas Non-Functional specifies quality attributes & constraints (Response time < 200 ms, 99.99% Availability, AES-256 Security, Portability).
💡 Exam Shortcut / Trap: Hinglish Tip: Verification = 'Building the product RIGHT' (Bina code run kiye static review/walkthrough/inspection); Validation = 'Building the RIGHT product' (Code run karke dynamic testing ki user ko jo chahiye tha wahi bana ya nahi)!

📖 Chapter 3: Analysis Tools & DFD — Structured Analysis Tools — Data Flow Diagrams (DFD Level 0/1/2), Balancing & Data Dictionary

5 Questions in Booklet
📌 3.1 Structured Analysis Tools — Data Flow Diagrams (DFD Level 0/1/2), Balancing & Data Dictionary
Key Formulas & Rules
  • 🔹 DFD Symbols (Yourdon / Gane-Sarson): Circle/Bubble = Process
  • 🔹 Arrow = Data Flow
  • 🔹 Open Rectangle/Parallel Lines = Data Store
  • 🔹 Square/Rectangle = External Entity (Source/Sink)
Simple Exam Points
  • Level 0 DFD (Context Diagram) represents the entire software system as a SINGLE process bubble interacting with external entities (it NEVER contains any Data Stores!).
  • DFD Balancing Rule: The net input and output data flows of a parent process bubble at Level k must exactly match the external input and output flows of its decomposed child DFD at Level k+1.
  • Illegal DFD Constructs (Strict Exam Rules): Data CANNOT flow directly without an intervening Process bubble: (1) External Entity -> External Entity (Illegal!), (2) External Entity -> Data Store or Data Store -> External Entity (Illegal!), (3) Data Store -> Data Store (Illegal!).
  • Also note: A DFD shows data flow, NEVER control flow, loops, or decision arrows (unlike a Flowchart)!
✅ Direct Exam Example: Data Dictionary (Metadata Repository): Defines the exact composition of every DFD data element using BNF-like notation: `=` (is composed of), `+` (AND / sequence), `[ | ]` (OR / selection), `{ }` (repetition/iteration), `( )` (optional).
💡 Exam Shortcut / Trap: Exam Trap: Context Diagram (Level 0 DFD) me poore system ko SIRF EK single Process Bubble se dikhaya jata hai aur usme koi Data Store nahi hota! Aur DFD me do External Entities ya External Entity aur Data Store ke beech direct arrow lagana 100% ILLEGAL hai!

📖 Chapter 4: Design: Coupling & Cohesion — Software Design — Modularity, Coupling (LOW) vs Cohesion (HIGH) & Spectrum Rankings

9 Questions in Booklet
📌 4.1 Software Design — Modularity, Coupling (LOW) vs Cohesion (HIGH) & Spectrum Rankings
Key Formulas & Rules
  • 🔹 Golden Design Principle: HIGH Cohesion (Intra-module single responsibility) + LOW Coupling (Inter-module independence)
Simple Exam Points
  • Coupling Spectrum (Best / Loosest to Worst / Tightest — Mnemonic 'D-S-C-E-C-C'): (1) Data Coupling (BEST — modules pass only primitive data parameters), (2) Stamp Coupling (pass composite data structure/record when only a few fields are needed), (3) Control Coupling (pass control flags/switches that dictate internal branching of another module), (4) External Coupling (share external hardware/device protocol), (5) Common Coupling (share global variables!), (6) Content Coupling (WORST — one module directly modifies or jumps into the internal code/data of another module!).
  • Cohesion Spectrum (Best / Strongest to Worst / Weakest — Mnemonic 'F-S-C-P-T-L-C'): (1) Functional Cohesion (BEST — all elements perform a single well-defined task), (2) Sequential (output of one part is input to next), (3) Communicational (operate on same input/output data structure), (4) Procedural, (5) Temporal (executed at same time, e.g., `init()` / startup routine), (6) Logical (grouped by category using switch flag), (7) Coincidental Cohesion (WORST — random unrelated functions thrown together).
✅ Direct Exam Example: Fan-In vs Fan-Out in Structure Charts: Fan-In is the number of calling modules that invoke Module M (HIGH Fan-In is desirable as it indicates code reuse!); Fan-Out is the number of subordinate modules directly called by Module M (keep Fan-Out <= 7 to avoid pancake complexity).
💡 Exam Shortcut / Trap: Hinglish Tip: Best Coupling = DATA Coupling; Worst Coupling = CONTENT Coupling! Best Cohesion = FUNCTIONAL Cohesion; Worst Cohesion = COINCIDENTAL Cohesion! Global variables share karna = Common Coupling.

📖 Chapter 5: Testing Strategies — Software Testing — Unit/Integration/System/Alpha-Beta, Black-Box (BVA/ECP) & McCabe Cyclomatic Complexity

14 Questions in Booklet
📌 5.1 Software Testing — Unit/Integration/System/Alpha-Beta, Black-Box (BVA/ECP) & McCabe Cyclomatic Complexity
Key Formulas & Rules
  • 🔹 McCabe's Cyclomatic Complexity V(G): (1) E − N + 2P
  • 🔹 (2) P_predicates + 1
  • 🔹 (3) Number of Enclosed Regions + 1
  • 🔹 Robust BVA (k variables) = 6k + 1 test cases (Standard BVA = 4k + 1)
Simple Exam Points
  • Testing Hierarchy: (1) Unit Testing (White-Box, tests individual functions/classes), (2) Integration Testing: Top-Down uses STUBS (dummy subordinate functions called by top module)
  • Bottom-Up uses DRIVERS (dummy main callers that invoke lower modules)
  • Sandwich/Hybrid combines both
  • Regression Testing re-runs test suite after code changes to ensure no new bugs were introduced
  • Smoke Testing is a shallow build-verification sanity check.
  • (3) Acceptance Testing: Alpha Testing (at Developer's site in controlled environment by internal users/testers) vs Beta Testing (at Customer's actual site in real environment by end-users).
  • White-Box Coverage Hierarchy: Path Coverage > Branch/Decision Coverage > Statement Coverage.
  • McCabe's V(G) equals the upper bound on the number of linearly independent paths needed for 100% Branch Coverage.
✅ Direct Exam Example: Worked Cyclomatic Complexity & BVA Math: A program control flow graph has 14 edges (E=14) and 10 nodes (N=10), or 5 `if/while` binary decision predicates. V(G) = 14 − 10 + 2 = 6 (also P + 1 = 5 + 1 = 6 independent paths). For a function with n = 3 input variables, Standard BVA test cases = 4(3) + 1 = 13; Robust BVA = 6(3) + 1 = 19.
💡 Exam Shortcut / Trap: Exam Trap: Top-Down Integration me 'STUBS' (dummy child) lagte hain, jabki Bottom-Up Integration me 'DRIVERS' (dummy parent caller) lagte hain! Aur n-variable Boundary Value Analysis (BVA) me Standard = `4n + 1` test cases aur Robust = `6n + 1` test cases bante hain!

📖 Chapter 6: Maintenance & Metrics — Software Maintenance Categories (Lientz-Swanson) & COCOMO / Function Point Estimation

8 Questions in Booklet
📌 6.1 Software Maintenance Categories (Lientz-Swanson) & COCOMO / Function Point Estimation
Key Formulas & Rules
  • 🔹 Basic COCOMO: Effort E = a · (KLOC)^b [Person-Months]; Development Time D = c · (E)^d [Months]
  • 🔹 Organic (a=2.4, b=1.05)
  • 🔹 Semi-Detached (a=3.0, b=1.12)
  • 🔹 Embedded (a=3.6, b=1.20)
Simple Exam Points
  • Four Categories of Software Maintenance (by Effort Share): (1) Perfective Maintenance (~50–60% — LARGEST share!
  • Enhancing functionality, improving performance, adding user-requested features), (2) Adaptive Maintenance (~25% — porting software to a new OS, hardware, database, or regulatory environment), (3) Corrective Maintenance (~20% — fixing latent bugs/defects discovered in production), (4) Preventive Maintenance (~5% — code refactoring/restructuring to improve future maintainability).
  • Function Point Analysis (Albrecht FPA): Computes Unadjusted Function Points (UFP) from 5 user-visible components (External Inputs EI, External Outputs EO, External Inquiries EQ, Internal Logical Files ILF, External Interface Files EIF), then multiplies by Value Adjustment Factor `VAF = 0.65 + 0.01 × Σ(F_i)` (where 14 GSC factors F_i ∈ [0..5], so VAF ranges from 0.65 to 1.35).
✅ Direct Exam Example: Worked Basic COCOMO Calculation: Estimate Effort for an Organic software project of size 32 KLOC (with a = 2.4, b ≈ 1.05; using simplified exponent 1.05: 32^1.05 ≈ 38). E = 2.4 × (32)^1.05 ≈ 91 Person-Months.
💡 Exam Shortcut / Trap: Hinglish Tip: Software Maintenance me sabse ZYADA kharcha (~55%) 'Perfective Maintenance' (naye features add karne) par hota hai, na ki Corrective (bug fixing ~20%) par! OS/Hardware upgrade ke liye change karna = 'Adaptive Maintenance'.

(C) Organic Mode -> Semi-Detached Mode -> Embedded Mode ✅

Answer (C): Organic Mode (small, experienced team, flexible) -> Semi-Detached Mode (medium, mixed team) -> Embedded Mode (large, tight hardware/real-time constraints) — Organic mode (`a=2.4, b=1.05`, 2–50 KLOC) is for small familiar business apps; Semi-Detached (`a=3.0, b=1.12`, 50–300 KLOC) is for compilers/DBMS; Embedded (`a=3.6, b=1.20`, >300 KLOC) is for avionics/RTOS.

📖 Chapter 7: Quality & CMM Levels — Software Quality Assurance, ISO 9001, SEI CMM / CMMI 5 Maturity Levels & Reliability Metrics

4 Questions in Booklet
📌 7.1 Software Quality Assurance, ISO 9001, SEI CMM / CMMI 5 Maturity Levels & Reliability Metrics
Key Formulas & Rules
  • 🔹 MTBF (Mean Time Between Failures) = MTTF (Mean Time To Failure) + MTTR (Mean Time To Repair)
  • 🔹 System Availability A = MTTF / (MTTF + MTTR) = MTTF / MTBF
Simple Exam Points
  • SEI Capability Maturity Model (CMM / CMMI) 5 Levels in Order (Mnemonic 'I-R-D-M-O'): Level 1: Initial (Ad-hoc, chaotic, heroic individual effort)
  • Level 2: Repeatable / Managed (basic project management, cost/schedule tracking, configuration management)
  • Level 3: Defined (organization-wide standardized, documented software engineering processes)
  • Level 4: Managed / Quantitatively Managed (statistical process control and quantitative quality metrics collected)
  • Level 5: Optimizing (continuous process improvement, defect prevention, and proactive innovation).
  • McCall's Quality Factors are grouped into 3 categories: Product Operation (Correctness, Reliability, Efficiency, Integrity, Usability), Product Revision (Maintainability, Flexibility, Testability), and Product Transition (Portability, Reusability, Interoperability).
✅ Direct Exam Example: Worked Availability Numerical: A server has Mean Time To Failure (MTTF) = 990 hours and Mean Time To Repair (MTTR) = 10 hours. Then MTBF = 990 + 10 = 1000 hours, and steady-state Availability = 990 / (990 + 10) = 990 / 1000 = 99.0%.
💡 Exam Shortcut / Trap: Exam Trap: SEI CMM ke 5 levels ka exact kram yaad rakhein: 1. Initial -> 2. Repeatable -> 3. Defined -> 4. Managed -> 5. Optimizing ('I-R-D-M-O')! Organization-wide standard process Level 3 (Defined) par aata hai.

Q7.4: If a mission-critical server has a Mean Time Between Failures (MTBF) of 1,000 hours and a Mean Time To Repair (MTTR) of 5 hours, what are its Mean Time To Failure (MTTF) and steady-state Operational Availability?
(A) MTTF = 1,005 hours and Operational Availability = 95.0%
(B) MTTF = 995 hours and Operational Availability = 99.5% ✅
(C) MTTF = 200 hours and Operational Availability = 99.9%
(D) MTTF = 995 hours and Operational Availability = 99.0%
Answer (B): Since MTBF = MTTF + MTTR, MTTF = 1000 − 5 = 995 hours, and Availability = MTTF / MTBF = 995 / 1000 = 0.995 = 99.5%.
